ArtifactFlow: install it on your server

No DevOps required. Three steps, and a prepared script does most of it for you.

What you need first

SSH access to your server ability to add 2 DNS records mail: SMTP details or a Resend key

Three steps

1

Run the installer

On the server, as the artifactflow user, from a clone of this repository:

git clone <repo url>   # first time only
cd artifactflow-podman
./install.sh

The script asks for your two hostnames and mail transport, generates all passwords and keys itself, builds and starts every service, prepares the database, and offers to create the first administrator. If something goes wrong it tells you exactly what and where to look.

It also asks whether to enable PDF artifacts. This is optional and off by default. If unsure, leave it off, you can enable it later with ./install.sh --enable-pdf.

Enabled PDF? Here is what to do extra

The installer already sets the PDF processor up safely: no network, one instance, strict memory and process limits. Before you rely on PDF in production, confirm the rest once:

  1. The artifactflow-pdf-processor service is healthy (systemctl --user status artifactflow-pdf-processor).
  2. Its startup log shows the containment filter active and the healthcheck passes (journalctl --user -u artifactflow-pdf-processor).
  3. Inside the app container, php artisan artifactflow:doctor reports no PDF error.
  4. Upload a test PDF: text is extracted and it renders from the artifact hostname.
  5. Do the preview check on Safari/iOS.
  6. Write down a short note that the above passed (your final sign-off).

Full checklist with the exact commands: TESTING.md, section "PDF enablement gate". Background on why: README.md, "PDF uploads".

2

Point two hostnames at the server

At your DNS provider add two A records to the server's IP (the installer prints it at the end):

artifactflow.example.com   ->  server IP
artifacts.example.com      ->  server IP

Why two? The blue box below explains. It can be the same server, this is just about two different names.

3

Turn on HTTPS (certificates)

The last piece, as root. The installer prints the exact commands at the end. In short:

certbot --nginx -d artifactflow.example.com
certbot --nginx -d artifacts.example.com

Certbot obtains the padlock (certificate) itself, for free. More in the amber box below.

Two things worth explaining

Why two hostnames?

The app can display content uploaded by users, and that content can carry its own code. To keep that foreign code away from your login and data, it is served from a separate hostname. The browser then treats it as a stranger and walls it off.

artifactflow.example.comThe app itself: login, your data. Trusted.
artifacts.example.comOnly displays uploaded artifacts. Separate, "behind a wall".

Think of two locked rooms in the same building: the second one has no key to the safe in the first. That is why it must be two different names, not the same one.

What are certificates (HTTPS)?

That is the padlock in the address bar. It makes the connection between the user and the server encrypted, and proves the hostname is really yours. Production will not even start without it.

You do not buy or hand-configure anything. The certbot tool obtains it for free with one command per hostname, and renews it too. That is why DNS (step 2) has to be done first: certbot needs to verify the hostname points at your server.

If something gets stuck: the installer prints what failed and where to look (usually journalctl --user -u artifactflow-app). Nothing breaks permanently, the script can be run again.
The detailed technical version is in README.md. This is the light version for the first run.
